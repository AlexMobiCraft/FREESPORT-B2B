### 🎯 Ключевые особенности архитектуры

- **API-First подход** с Django REST Framework
- **Монорепо структура** для управления несколькими брендами
- **Роле-ориентированное ценообразование** для B2B/B2C
- **Двусторонняя интеграция с 1С** (товары, клиенты, заказы)
- **Microservice-ready архитектура** для масштабирования
- **Comprehensive testing strategy** с 70%+ покрытием

### 📅 История изменений

- **2026-09-10:** Epic 41 / Story 41.9, седьмой круг ревью — отказ `consent_text_outdated` несёт в поле версии одно и то же требование обновить страницу при любой ошибке этого поля: прежде массив, объект или boolean давали «Not a valid string.», а ноль-байт и одиночный суррогат — тексты валидаторов `CharField` (`11-security-performance.md`, §5.1). Контракт API не менялся — схема `ConsentTextOutdatedResponse` текст сообщения не фиксирует
- **2026-09-10:** Epic 41 / Story 41.9, шестой круг ревью — хеш в версии формулировки согласия удлинён с 8 до 32 hex (128 бит): при 8 hex коллизия подбиралась перебором, и две разные формулировки могли получить одну версию (`11-security-performance.md` §5.1, `02-data-models.md`, `09-database-schema.md`, пример payload в `18-b2b-verification-workflow.md`). Повторная подписка уже активного email теперь фиксирует обе записи `UserConsent`, а не отвечает нейтральным успехом без записи; то же при гонке на уникальном email (§5.1). Контракт API не менялся — изменилось только значение версии в примере запроса подписки
- **2026-09-10:** Epic 41 / Story 41.9, пятый круг ревью — версии формулировок согласия сверяются field-level валидаторами сериализаторов, а не в object-level `validate()`: машинный код `consent_text_outdated` больше не теряется, если в запросе есть другие ошибки (email, роль, галочка, несовпадение паролей) (`11-security-performance.md`, §5.1). Контракт API не менялся — свежая схема `spectacular` структурно равна `docs/api/openapi.yaml`
- **2026-09-10:** Epic 41 / Story 41.9, четвёртый круг ревью — обе формы ответа `400` эндпоинтов с согласием стали именованными схемами (`FieldValidationErrorResponse`, `ConsentTextOutdatedResponse`, `oneOf` в `ConsentValidationErrorResponse`), у `UserRegistrationRequest` появилась условная обязательность `marketing_consent_text_version` через `if`/`then` (OpenAPI 3.1). Индексы `common_userconsent` в DDL заменены фактическими именами из `pg_indexes` (`09-database-schema.md`), пример payload B2B-регистрации дополнен consent-полями (`18-b2b-verification-workflow.md`), compliance-гарантии ослаблены до фактически обеспеченных: версия текста подтверждает совместимость официального бандла, а не факт показа; append-only держится путями кода, а не схемой; база проверяет допустимость `source`, но лишь непустоту версии (`11-security-performance.md`, `02-data-models.md`)
- **2026-09-09:** Epic 41 / Story 41.9 — аудитируемость журнала согласий: поля `source` и `consent_text_version` у `UserConsent` (`02-data-models.md`), DDL с двумя CHECK-ограничениями и двумя индексами плюс миграция `0019` (`09-database-schema.md`), реестр `consent_texts.json` / `consent_texts.py` (`04-component-structure.md`), раздел об аудитируемости формулировки (`11-security-performance.md`), исправлено устаревшее с 2026-09-05 утверждение о несоздании `UserConsent` при привязке к 1С (`18-b2b-verification-workflow.md`). По итогам ревью добавлена сверка версии: формы присылают версию показанной формулировки, сервер отклоняет устаревшую (`400 consent_text_outdated`) — контракт `SubscribeRequest` / `UserRegistrationRequest` расширен, история ревизий страхуется сверкой с разделом `known_versions`. Вторым кругом ревью источник ограничен перечислением на уровне БД (`userconsent_source_valid`, миграция `0020`) — `choices` базы не касаются
- **2026-05-09:** Epic 35 / Story 35.1 — добавлены `UserConsent` (audit log согласий 152-ФЗ) в `02-data-models.md`, реальная схема `common_userconsent` в `09-database-schema.md`, страница `/privacy-policy` в `04-component-structure.md`, раздел compliance в `11-security-performance.md`
- **2026-05-02:** Актуализированы модели данных, API и 1С-документация под `customer_code`, канонические `order_number` и master/sub-order flow
- **2025-09-05:** Добавлена архитектура интеграции с 1С, включая синхронизацию покупателей
- **2025-08-23:** Исправления Docker конфигурации и система изоляции тестов
