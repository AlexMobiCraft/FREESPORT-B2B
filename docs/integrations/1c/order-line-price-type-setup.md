# Заказы сайта → 1С: вид цены в строках и соглашение акции

Регламент для администратора 1С. Настройка делается в 1С в настройке обмена БУС (режим `<Свой алгоритм>`), без правок расширения БУС. Разбор механики — в [исследовании](../../../_bmad-output/implementation-artifacts/research-order-line-price-type-1c.md), решения владельца — в [спеке](../../../_bmad-output/implementation-artifacts/spec-order-line-price-type-1c.md).

## Зачем это нужно

В заказах с сайта `ЗаказКлиента.Товары.ВидЦены` пуст во всех строках, а соглашение всегда «Стандартное». Менеджеры оформляют иначе: акционная позиция идёт по виду цен акции, остальные — по виду цен клиента, соглашение — «Акция …».

После настройки:

| Реквизит                | Значение в загруженном заказе                                                                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Товары.ВидЦены` | вид цен, по которому сайт посчитал цену строки: акция, «Опт N», «РРЦ» и т. д.                                                            |
| Соглашение            | действующее соглашение с именем вида цен акции, если в заказе есть акционная строка; иначе «Стандартное» |

## Что присылает сайт

Сайт фиксирует вид цены строки в момент оформления заказа — это вид цен того поля, из которого взята цена, а не роль клиента.

| Где в XML                                                                                                 | Что                                                              | Кто читает                                               |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Строка: `ЗначенияРеквизитов` → `ВидЦеныИд`                              | GUID вида цен 1С                                            | алгоритм строки `ВидЦены` (ниже)       |
| Строка: `<ВидЦены><Ид/><Наименование/></ВидЦены>`                         | тот же вид цен                                           | БУС не читает; для совместимости       |
| Шапка: `<Соглашение><Наименование>` и реквизит «Соглашение» | имя вида цен акции или «Стандартное» | алгоритм строки «Соглашение» (ниже) |

Особые случаи:

- у поля цены нет активного вида цен на сайте (например, цена представителя федерации) — строка уходит без `<ВидЦены>` и без `ВидЦеныИд`, `Товары.ВидЦены` останется пустым;
- заказы, оформленные до выката, уходят как раньше: `<ВидЦены>` по роли, без `ВидЦеныИд`, соглашение «Стандартное»;
- соглашение решается отдельно для каждого документа (субзаказа): «Акция …» получает только тот документ, в котором есть акционная строка.

## Порядок выката

**Сайт можно выкатывать раньше настройки 1С.** Пока строки соответствия не настроены, БУС не читает ни `<ВидЦены>`, ни `ВидЦеныИд`, ни соглашение из XML: документ создаётся как раньше (вид цены пуст, соглашение «Стандартное»). Это следует из разбора кода БУС 8.1.0.40 ([исследование](../../../_bmad-output/implementation-artifacts/research-order-line-price-type-1c.md), п. 2) и подтверждено загрузкой 14.11.2026: заказ A из раздела «Проверка на test_base» на ненастроенном узле дал документ с пустым `ВидЦены` и «Стандартным» соглашением. На проде стоит БУС 8.1.0.45 — эту версию загрузкой не проверяли; если сомневаетесь, выкатывайте сайт вместе с настройкой 1С. Настройку 1С включают после проверки на `test_base`.

## Условие: имя соглашения акции = имя вида цен акции

Сайт передаёт в шапке **имя вида цен** акции, а алгоритм ищет **соглашение** с таким же именем. В `test_base` они совпадают («Акция МАРТ»). На проде вид цен называется «АКЦИЯ НОЯБРЬ-26» — сверьте, что соглашение называется так же, и держите это правило для каждой новой акции. Регистр букв поиск не различает, но лишние пробелы и другие символы — различает. Не найдено ровно одно действующее соглашение — заказ получит «Стандартное», ошибки не будет.

## К каким настройкам применять

К каждой настройке обмена БУС, которая загружает заказы («Загружать заказы = Да»). Для схемы из [регламента «По расписанию»](./orders-pull-schedule-setup.md) это настройка Б; настройку А («В режиме реального времени») не трогать.

## Перед применением

1. Сохраните скриншоты таблицы соответствий «Заказ клиента»: строка «Соглашение» шапки и строки табличной части «Товары» (`КодСтроки`, `ВидЦены`). Это исходное состояние для отката.
2. Узнайте GUID соглашения «Стандартное» **на той базе, которую настраиваете** (на проде — тот, что сейчас стоит фиксированным значением в строке «Соглашение»). В `test_base` это `2c0a6c2f-bd0d-11ea-81c4-00155d3cae02`. Если GUID берёте из навигационной ссылки (`…?ref=81c400155d3cae0211eabd0d2c0a6c2f`), 32 символа после `ref=` переставлены: GUID = символы 25–32, 21–24, 17–20, 1–4, 5–16 (`2c0a6c2f` `bd0d` `11ea` `81c4` `00155d3cae02`).
3. Если [регламент «Менеджер и Подразделение»](./order-manager-author-department-setup.md) на этой базе ещё не применён, строка «Менеджер» работает предопределённым алгоритмом и берёт менеджера **из соглашения**. Тогда у заказов с соглашением «Акция …» Менеджер станет менеджером этого соглашения. Проверьте поле «Менеджер» соглашений акций или сначала примените тот регламент.
4. Проверено разбором кода БУС 8.1.0.40 (`test_base`). На проде стоит 8.1.0.45 — проверку из раздела «Проверка на проде» выполните обязательно.

## Шаги

> Названия кнопок и переключателей формы настройки сверьте на экране: важны строки таблицы, их порядок и тексты алгоритмов, а не внешний вид формы.

На `test_base` до шагов выполните заказ A из раздела «Проверка на test_base» — после шагов ненастроенного узла для него уже не будет.

1. Откройте настройку обмена БУС → документ «Заказ клиента» → форму заполнения реквизитов загружаемого документа. Включите **расширенный режим** (только в нём для строк доступен тип «<Свой алгоритм>»).
2. **Шапка, строка «Соглашение»:** тип «<Свой алгоритм>», значение — текст «Алгоритм соглашения» ниже. В его первой строке `<GUID «Стандартное»>` — заготовка: замените её GUID из п. 2 раздела «Перед применением», кавычки оставьте. Для `test_base`:

   ```bsl
   // было (в тексте ниже)
   [Результат] = Справочники.СоглашенияСКлиентами.ПолучитьСсылку(Новый УникальныйИдентификатор("<GUID «Стандартное»>"));
   // должно стать
   [Результат] = Справочники.СоглашенияСКлиентами.ПолучитьСсылку(Новый УникальныйИдентификатор("2c0a6c2f-bd0d-11ea-81c4-00155d3cae02"));
   ```

   Без замены алгоритм падает на первой строке, и **ни один заказ** через настройку не загрузится.
3. **Табличная часть «Товары», строка «ВидЦены»** (в `test_base` она уже заведена: «Фиксированное значение», пусто): тип «<Свой алгоритм>», значение — «Алгоритм вида цены строки» ниже.
4. **Проверьте порядок строк «Товары»:** `КодСтроки` должна стоять **выше** `ВидЦены`. Алгоритм ищет свою строку XML по `КодСтроки`; если `ВидЦены` окажется выше, вид цены останется пустым.
5. Сохраните настройку. Остальные строки не меняйте.

Требования к текстам: вставлять без изменений, отступы — табуляции, переводы строк должны сохраниться.

Как устроены оба алгоритма: любое исключение в `<Свой алгоритм>` роняет загрузку всего документа, поэтому работа с данными заказа (разбор XML, запрос, поиск строки) стоит внутри `Попытка` с пустой веткой `Исключение`. До `Попытка` алгоритм первым делом присваивает `[Результат]` резервное значение — «Стандартное» или пустой вид цен. Поэтому при любом исключении внутри `Попытка` результат остаётся резервным, а не пустым.

Единственное, что намеренно стоит вне `Попытка`, — проверка GUID «Стандартного» в алгоритме соглашения. Опечатка в GUID, GUID с другой базы или помеченное на удаление «Стандартное» — ошибка настройки, а не данных заказа: загрузка падает с понятным текстом на первом же тестовом заказе, а не создаёт документы со ссылкой на несуществующее или удаляемое соглашение.

### Алгоритм соглашения

```bsl
[Результат] = Справочники.СоглашенияСКлиентами.ПолучитьСсылку(Новый УникальныйИдентификатор("2c0a6c2f-bd0d-11ea-81c4-00155d3cae02"));
Если НЕ ОбщегоНазначения.СсылкаСуществует([Результат]) ИЛИ [Результат].ПометкаУдаления Тогда
	ВызватьИсключение "Алгоритм соглашения: соглашения «Стандартное» с GUID из настройки обмена нет в базе или оно помечено на удаление";
КонецЕсли;
Попытка
	Реквизиты = [ДокументXML].ЗначенияРеквизитов;
	Найд = ?(Реквизиты = Неопределено, Неопределено, Реквизиты.Найти("Соглашение", "Наименование"));
	Если Найд <> Неопределено И ЗначениеЗаполнено(Найд.Значение) Тогда
		Запрос = Новый Запрос("ВЫБРАТЬ ПЕРВЫЕ 2 С.Ссылка КАК Ссылка ИЗ Справочник.СоглашенияСКлиентами КАК С
		|ГДЕ С.Наименование = &Имя И НЕ С.ПометкаУдаления
		|	И С.Статус = ЗНАЧЕНИЕ(Перечисление.СтатусыСоглашенийСКлиентами.Действует)
		|	И (С.ДатаНачалаДействия = ДАТАВРЕМЯ(1, 1, 1) ИЛИ С.ДатаНачалаДействия <= &Дата)
		|	И (С.ДатаОкончанияДействия = ДАТАВРЕМЯ(1, 1, 1) ИЛИ С.ДатаОкончанияДействия >= &Дата)");
		Запрос.УстановитьПараметр("Имя", Найд.Значение);
		Запрос.УстановитьПараметр("Дата", НачалоДня(ТекущаяДатаСеанса()));
		Выборка = Запрос.Выполнить().Выбрать();
		Если Выборка.Количество() = 1 И Выборка.Следующий() Тогда
			[Результат] = Выборка.Ссылка;
		КонецЕсли;
	КонецЕсли;
Исключение
КонецПопытки;
```

Соглашение ищется только среди действующих: без пометки удаления, со статусом «Действует», текущая дата в периоде действия, и найдено **ровно одно**. Иначе — «Стандартное». Условие по статусу обязательно: среди непомеченных соглашений есть одноимённые («РАСПРОДАЖА», «Соглашение реализации» и др.). Найденное запросом соглашение существует и не помечено на удаление по построению; `ПолучитьСсылку` же ни существование, ни пометку не проверяет, поэтому «Стандартное» проверяется отдельно: `СсылкаСуществует` и `ПометкаУдаления`. `ИЛИ` в 1С вычисляется сокращённо: у несуществующей ссылки `ПометкаУдаления` не читается.

### Алгоритм вида цены строки

```bsl
[Результат] = Справочники.ВидыЦен.ПустаяСсылка();
Попытка
	Для Каждого СтрXML Из [ДокументXML].Товары Цикл
		Если СтрXML.КодСтроки <> [НоваяСтрока].КодСтроки Тогда Продолжить; КонецЕсли;
		Если СтрXML.ЗначенияРеквизитов <> Неопределено Тогда
			Найд = СтрXML.ЗначенияРеквизитов.Найти("ВидЦеныИд", "Наименование");
			Если Найд <> Неопределено И ЗначениеЗаполнено(Найд.Значение) Тогда
				Ссылка = Справочники.ВидыЦен.ПолучитьСсылку(Новый УникальныйИдентификатор(Найд.Значение));
				Если ОбщегоНазначения.СсылкаСуществует(Ссылка) И НЕ Ссылка.ПометкаУдаления Тогда
					[Результат] = Ссылка;
				КонецЕсли;
			КонецЕсли;
		КонецЕсли;
		Прервать;
	КонецЦикла;
Исключение
	[Результат] = Справочники.ВидыЦен.ПустаяСсылка();
КонецПопытки;
```

Почему так:

- плейсхолдер `[СтрокаXML]` в БУС 8.1.0.40 не работает (ключа нет в параметрах алгоритма), поэтому строка XML ищется в `[ДокументXML].Товары` по `КодСтроки` строки документа;
- вид цен ищется **по GUID**, не по наименованию: имена видов цен неуникальны без учёта регистра;
- сайт не передаёт в строке `НомерПозицииКорзины`: БУС подменил бы им `КодСтроки`, по которому работает алгоритм.

## Проверка на test_base

Заказы подаются в БУС **через локальный сайт**: сайт в Docker (`localhost:8001`) и настройка БУС в `test_base` по [регламенту «По расписанию»](./orders-pull-schedule-setup.md) с адресом локального сайта («Загрузка заказов локально»). Раз в 300 с БУС запрашивает у сайта новые заказы (`mode=query`) и загружает их. Так проверка прошла 13.11.2026. Подать в БУС готовый XML-файл напрямую никто не проверял, поэтому [`samples/order-line-price-type-test-base.xml`](./samples/order-line-price-type-test-base.xml) — только образец того, что присылает сайт, а не файл для загрузки.

Номер, дату и время документа, наименования и цены строк, вид цены и соглашение формирует код выгрузки сайта. Поэтому каждый заказ даёт **новый** документ, датированный днём проверки, и в XML нечего согласовывать вручную. Дату запрета изменения данных `test_base` всё же сверьте: она не должна закрывать текущий день, иначе документ не проведётся.

Проверка — три заказа: **A** — новый формат до настройки, **B** — новый формат после настройки, **C** — старый формат после настройки.

### Подготовка

Команды ниже выполняйте в Git Bash из корня репозитория: восстановление акции читает файл через перенаправление ввода `<`, которого нет в Windows PowerShell.

1. **Клиент.** Оптовая учётная запись на локальном сайте, верифицированная, контрагент которой есть в `test_base`. 13.11.2026 использовалась `tmp-mgrtest-t1` (Опт 3).
2. **Товары.** Два варианта, чья номенклатура есть в `test_base`, с ценой роли клиента: один пойдёт по акции, другой — нет. 13.11.2026 акционным был вариант 2506 (бассейн). У обоих должны совпадать **ставка НДС и склад**: сайт делит заказ на субзаказы по паре «ставка НДС + склад», и при разных значениях заказ с обоими товарами уйдёт двумя документами, а документ с акционной и неакционной строкой проверен не будет. Ставку и склад покажет проверка из п. 7.
3. **Акция в `test_base`.** Выберите вид цен акции и одноимённое соглашение, которое действует **сегодня** (статус «Действует», текущая дата в периоде действия). Если такого нет, временно продлите срок соглашения и запишите исходную дату для отката. 13.11.2026: вид цен и соглашение «Акция МАРТ», GUID вида цен `a151b0b5-160d-11f1-973b-f9cdeb93e398`, срок продлён до 31.12.2026.
4. **Сохраните состояние акции локального сайта.** Шаг 5 сделает тестовую акцию текущей. Прежняя акция при этом выключится, а акционные цены **всех** вариантов сбросятся. Одного включения прежней акции после проверки мало: её цены уже не вернутся. Кроме того, тип цен с GUID акции из п. 3 может уже быть на локальном сайте (например, пришёл импортом из 1С). Тогда шаг 5 изменит его, а не создаст новый, и после проверки его надо вернуть, а не удалить. Поэтому до шага 5 сохраните в файл вне репозитория текущую акцию, все акционные цены и состояние типа цен с GUID из п. 3. Подставьте GUID и наименование вида цен акции из п. 3 в первые две строки:

   ```bash
   G='<GUID вида цен акции из п. 3>'
   N='<наименование вида цен акции из п. 3, в точности как в test_base>'
   f=~/promo-backup-test-base.json
   if [ -e "$f" ]; then echo "СТОП: $f уже есть — прошлая проверка не восстановлена"; else
   docker compose --env-file .env -f docker/docker-compose.yml exec -T backend python manage.py shell --no-imports -c "
   import json
   from django.db import transaction
   from django.db.migrations.recorder import MigrationRecorder
   from apps.products.models import PriceType, ProductVariant
   from apps.products.services.promo import current_promo_type, lock_promo_state
   G, N = '$G', '$N'
   assert G.strip() and N.strip() and '<' not in G + N, 'не подставлены GUID или наименование'
   with transaction.atomic():
       lock_promo_state()
       db = str(MigrationRecorder.Migration.objects.order_by('pk').values_list('applied', flat=True).first())
       p = current_promo_type()
       t = PriceType.objects.filter(onec_id=G).first()
       prices = {str(pk): str(v) for pk, v in ProductVariant.objects.filter(promo_price__isnull=False).values_list('pk', 'promo_price')}
   print(json.dumps({'db': db, 'test_guid': G, 'test_name': N, 'test_type': {k: getattr(t, k) for k in ('onec_name', 'product_field', 'user_role', 'is_active')} if t else None, 'promo_type_pk': p.pk if p else None, 'promo_type_name': p.onec_name if p else None, 'prices': prices}))
   " > "$f.tmp" && mv "$f.tmp" "$f" && echo "копия сохранена: $f"
   fi
   ```

   - Акция, тип цен и цены читаются в одной транзакции под исключительной блокировкой состояния акции. Пока копия снимается, ни смена акции, ни импорт цен ничего не изменят, поэтому копия согласована.

### Заказ C: старый формат после настройки

Проверяет заказы, оформленные до выката сайта: у их строк нет снимка вида цены, и сайт выгружает их по-старому — `<ВидЦены>` по роли клиента, без `ВидЦеныИд`, соглашение «Стандартное».

Снимок надо стереть до того, как БУС получит заказ. `sent_to_1c = False` этого не гарантирует: XML уходит в БУС в ответе на `mode=query`, а отметку `sent_to_1c` сайт ставит позже — на следующем запросе или подтверждении. Заказ, у которого `sent_to_1c` ещё `False`, может уже лежать в БУС в новом формате. Поэтому заказ C оформляется при остановленном обмене:

2. **Дождитесь, пока БУС перестанет обращаться к сайту.** Через 6 минут после выключения (интервал расписания — 300 с) проверьте, что за эти 6 минут запросов заказов не было:

   ```bash
   if L=$(docker compose --env-file .env -f docker/docker-compose.yml logs --since 6m backend); then echo "запросов заказов за 6 минут: $(printf '%s\n' "$L" | grep -c 'mode=query')"; else echo "ОШИБКА: логи backend не получены, проверка не пройдена"; fi
   ```

   Ожидается `запросов заказов за 6 минут: 0`. Любое другое число значит, что задание ещё работает или выключено не то: повторите проверку через 6 минут, не оформляя заказ. `ОШИБКА` значит, что логи не прочитаны, и об остановке обмена команда ничего не говорит: устраните ошибку Docker и повторите. Логи читаются отдельно от подсчёта именно поэтому: в конвейере `logs | grep -c` ошибка `docker compose` тоже дала бы `0`.

   Чтобы `0` что-то значил, backend должен писать эти запросы в лог: до выключения задания (шаг 1) та же команда показывает число больше нуля — строки вида `POST /api/integration/1c/exchange/?type=sale&mode=query…`.        assert cur and cur.onec_id == b['test_guid'], 'текущая акция ' + (cur.onec_name if cur else 'отсутствует') + ', а не тестовая: восстановление остановлено'
   ```bash
       now = {k: getattr(cur, k) for k in F}
       assert now == {'onec_name': b['test_name'], 'product_field': 'promo_price', 'user_role': '', 'is_active': True}, 'тип цен акции изменён после п. 5 (' + str(now) + '): восстановление остановлено'
       if b['test_type'] is None:
           delete_price_types([cur])
       else:
           for k, v in b['test_type'].items():
               setattr(cur, k, v)
           save_price_type(cur)
       if b['promo_type_pk']:
           activate(PriceType.objects.get(pk=b['promo_type_pk']))
       ProductVariant.objects.filter(promo_price__isnull=False).update(promo_price=None)
       lost = [pk for pk, v in b['prices'].items() if not ProductVariant.objects.filter(pk=int(pk)).update(promo_price=Decimal(v))]
       sync_promo_flags()
   print('акция:', b['promo_type_name'] or 'нет', '| тип цен', b['test_guid'], 'удалён' if b['test_type'] is None else 'возвращён', '| цен восстановлено:', len(b['prices']) - len(lost), 'из', len(b['prices']))
   if lost:
       print('НЕПОЛНО: вариантов нет в базе, pk:', ', '.join(lost), '— копию не удаляю')
       sys.exit(3)
   " < "$f" && rm "$f" && echo "копия удалена: $f"
   ```

   Команда работает в одной транзакции под исключительной блокировкой состояния акции:

   - сверяет, что копия снята с этой же базы, текущая акция — тестовая и её тип цен всё ещё в тестовом состоянии из п. 5 «Подготовки»;
   - убирает тестовый тип цен: созданный для проверки — удаляет, существовавший до неё — возвращает ему прежние наименование, поле товара, роль и активность;
   - снова делает прежнюю акцию текущей;
   - стирает акционные цены, заданные для проверки, и возвращает прежние;
   - пересчитывает флаг «Акция» у товаров.

   Ошибка на любом этапе откатывает всё: сайт остаётся в состоянии проверки, и команду можно запустить снова. Параллельная смена акции или импорт цен ждёт конца транзакции, а не вклинивается между этапами.

   Ожидается `цен восстановлено: N из N`, затем `копия удалена`. Если до проверки акции не было — `акция: нет | … | цен восстановлено: 0 из 0`.

   `AssertionError` или `PriceType.DoesNotExist` — команда ничего не изменила, копия на месте:

   - «другой или пересозданной базы» — локальная база не та, в которой снималась копия: `pk` вариантов в копии к ней не относятся. Ничего не восстанавливайте; копия годится только для своей базы.
   - «текущая акция …, а не тестовая» — акцию сменили или выключили во время проверки. Если неизвестно, дошла ли проверка до п. 5, запустите «Проверьте копию» (п. 4 «Подготовки»): `копия годна` значит, что сайт не менялся, и копию можно удалить вручную.
   - «тип цен акции изменён после п. 5» — в скобках его текущие поля. Команда не затирает чужие правки: выясните, кто и зачем менял тип. Если правка случайная — верните поля по таблице п. 5 «Подготовки» и запустите команду снова; если нужная — восстановите акцию и цены вручную, прежние значения — в копии.
   - `PriceType.DoesNotExist` — за время проверки удалили прежнюю акцию.

   `НЕПОЛНО: вариантов нет в базе` — восстановление **записано**, но части вариантов за время проверки не стало; команда завершается с кодом 3 и копию **не удаляет**. Не удаляйте её и вручную, пока не выясните, кто удалил перечисленные варианты: файл — единственный список их прежних акционных цен. Повторный запуск команды не нужен и остановится на проверке текущей акции. Когда разберётесь — `rm ~/promo-backup-test-base.json`; пока файл есть, п. 4 «Подготовки» следующей проверки останавливается.

## Проверка на проде

1. **Выберите клиента Опт N и два товара и проверьте строки будущего заказа до оформления.** Товар из акции ещё не гарантирует акционную строку: если его акционная цена выше цены роли клиента, сайт возьмёт цену роли. Неакционный товар без своей цены роли пойдёт по рознице, а поле без активного типа цен уйдёт без вида цен. Запустите на сервере прода, из каталога проекта, ту же команду, что в п. 7 «Подготовки» раздела «Проверка на test_base», заменив в ней `--env-file .env -f docker/docker-compose.yml` на `--env-file .env.prod -f docker/docker-compose.prod.yml`. Команда только читает и в базу ничего не пишет. Ожидается:

   | Что               | Товар из акции                                                                                                             | Товар без акции                      |
   | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
   | поле цены    | `promo_price`                                                                                                                        | поле роли клиента (`optN_price`) |
   | вид цен        | текущая акция — её имя совпадает с именем соглашения акции (см. «Условие») | «Опт N …»                                   |
   | GUID товара    | заполнен                                                                                                                       | заполнен                                  |
   | НДС и склад | совпадают у обоих, если нужен один документ (иначе — п. 5)                                  |                                                   |

   `retail_price` у оптового клиента — учётная запись не верифицирована или цены роли у варианта нет; `НЕТ` в столбце вида цен — для поля нет активного типа цен. В обоих случаях выберите другой товар или клиента и проверьте снова: иначе ожидания п. 4 не наступят, и проверка ничего не скажет о настройке 1С.
2. Оформите на сайте контрольный заказ этим клиентом с этими двумя товарами.
3. Через ≈5 минут (расписание настройки Б — 300 с) найдите документ в 1С: номер вида `СМУТ-…`, номер сайта — в комментарии `[Номер документа на сайте: …]`.
4. Проверьте: у каждой строки `ВидЦены` — тот вид цен, что показала проверка п. 1 (у акционной — вид цен акции, у второй — «Опт N»); соглашение — соглашение акции; цены и суммы совпадают с заказом на сайте; в журнале БУС нет ошибок.
5. Если в заказе позиции с разными ставками НДС или складами, сайт отправит несколько документов: «Акция …» получит только документ с акционной строкой.
6. **Снимите резерв контрольного заказа.** Сайт передаёт строки с действием «Резервировать», настройка Б проводит документ — товар контрольного заказа зарезервирован на складе. Отменить заказ на сайте уже нельзя: после выгрузки он переходит в статус «В обработке», и отмена из личного кабинета отвечает ошибкой, а флаг «Отменен» в XML всегда `false`. Поэтому снимайте резерв в 1С:

   1. пометьте документ (каждый, если их несколько) на удаление — платформа при этом отменяет проведение, и движения документа, в том числе резерв, удаляются;
   2. проверьте: документ помечен на удаление и не проведён; в отчёте «Остатки и доступность товаров» (Склад и доставка → Отчеты по складу → Анализ запасов) по товарам заказа резерв под него не числится;
   3. на сайте в админке поставьте заказу и его субзаказам статус «Отменен», чтобы у клиента он не висел «В обработке».

## Ограничения

- **«Заполнить цены по соглашению» затирает цены сайта.** Если менеджер нажмёт его в заказе с соглашением «Акция …», УТ пересчитает строки по соглашению (вне ТЧ акции — «Опт 1»).
- Уже загруженные заказы не дозаполняются; настройка действует на новые.
- Каждая новая акция — новое соглашение с тем же именем, что и вид цен акции (см. «Условие»).
- Повторяйте проверку после каждого обновления расширения БУС: алгоритмы опираются на внутренние параметры `[ДокументXML]` и `[НоваяСтрока]`.
